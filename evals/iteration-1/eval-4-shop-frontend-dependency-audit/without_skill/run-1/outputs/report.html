F-01

colour-utilz@1.0.0 has the structure of a malicious install-time dropper (currently inert)

High
Files
node_modules/colour-utilz/package.json line 1 (scripts.postinstall); node_modules/colour-utilz/setup.js lines 1–3; node_modules/colour-utilz/index.js line 1
Standards
CWE-506 (Embedded Malicious Code, as a pattern), CWE-829 (Inclusion of Functionality from Untrusted Control Sphere); MITRE ATT&CK Enterprise T1195.001 (Compromise Software Dependencies and Development Tools), T1027 (Obfuscated Files or Information), T1059.007 (JavaScript); OWASP Top 10:2025 A03 Software Supply Chain Failures
Advisory DBs
No record in OSV.dev or the GitHub Advisory Database (checked any version, including malware advisories). This is expected for a package that is not on public npm. It does not show the package is safe.

Evidence

// node_modules/colour-utilz/package.json
{"name": "colour-utilz", "version": "1.0.0", "main": "index.js", "scripts": {"postinstall": "node setup.js"}}

// node_modules/colour-utilz/setup.js
1  // Inert test fixture: the encoded string decodes to a harmless comment and nothing runs it.
2  const p = "Ly8gaGFybWxlc3MgdGVzdCBmaXh0dXJl";
3  if (false) { eval(Buffer.from(p, "base64").toString()); }

// node_modules/colour-utilz/index.js
1  module.exports = {};

Why it looks malicious

  1. It runs at install time. postinstall: node setup.js runs automatically on npm install or npm ci, before anyone imports the package.
  2. It has an obfuscated loader. A base64 string is decoded and passed to eval(). This is the usual shape of npm malware, because it hides the real payload from code review and simple scanners.
  3. It has no functionality. The "colour utilities" package exports an empty object. A package with no code has no legitimate reason to run an install script.
  4. Its name is a lookalike. colour-utilz differs from the existing npm package colour-utils (latest 1.2.4) by one letter. Swapping "z" for "s" is a common typosquatting pattern.
  5. Its provenance cannot be verified. It comes from a non-public host with no integrity hash and no author, repository or license metadata (see F-02).

What it does today

I checked this by decoding the string, not by running anything. I also did not rely on the file's own "inert" comment, because comments are written by the package author. The eval sits behind if (false), so it never runs. The encoded string decodes to // harmless test fixture, which is just a JavaScript comment. Running this postinstall as shipped does nothing.

It is still rated High. All the scaffolding for a dropper is in place, and two small edits (flip false, swap the string) would make it live. Because the lockfile has no integrity hash for this package (F-02), npm would not notice if the tarball changed. This rating covers the risk of the package, not a confirmed compromise.

Fix

  • Remove colour-utilz from package.json. Find out who added it and why.
  • If it is a genuine internal library, get its source from the owning team, remove the postinstall hook, and republish it under a scoped name (see F-02).
  • If any machine or CI runner ever installed this project, compare the tarball served by packages.example.internal with the on-disk copy. There is no lockfile hash to check against, so a manual comparison is the only way to confirm it matches.
F-02

colour-utilz is open to dependency confusion and has no integrity pin

High
Files
package-lock.json line 6; package.json line 1. There is no project-level .npmrc.
Standards
CWE-494 (Download of Code Without Integrity Check), CWE-829; OWASP Top 10:2025 A08 Software or Data Integrity Failures and A03 Software Supply Chain Failures; MITRE ATT&CK Enterprise T1195.001

Evidence

// package-lock.json, line 6 (no "integrity" field)
"node_modules/colour-utilz": {"version": "1.0.0", "resolved": "https://packages.example.internal/colour-utilz-1.0.0.tgz"}

GET  https://registry.npmjs.org/colour-utilz                     -> 404 {"error":"Not found"}   (2026-10-14)
HEAD https://registry.npmjs.org/colour-utilz/-/colour-utilz-1.0.0.tgz -> 404

Risk

The package name is unscoped and unclaimed on the public npm registry, so anyone can publish colour-utilz@1.0.0 there. A developer laptop or CI runner where the internal registry is not configured would resolve the name from public npm and run that package's postinstall. The project ships no .npmrc, and regenerating the lockfile has the same effect. This is the "dependency confusion" technique (Alex Birsan, 2021). Separately, the lockfile has no integrity value, so npm cannot detect a swapped tarball, even when it is served by the internal host.

Fix

  • Move internal packages to a scope you control, for example @yourorg/colour-utils. Pin that scope to the internal registry in a committed .npmrc (@yourorg:registry=https://packages.example.internal/).
  • Regenerate the lockfile so every entry records an integrity hash.
  • Optionally, reserve the unscoped name on public npm as a placeholder.
F-03

expresss is a typosquat of express, locked to a version that does not exist

High
Files
package.json line 1 ("expresss": "4.18.2"); package-lock.json line 5
Standards
CWE-829, CWE-494; OWASP Top 10:2025 A03 Software Supply Chain Failures; MITRE ATT&CK Enterprise T1195.001
Advisory DBs
No OSV or GitHub Advisory Database record for expresss (any version, including malware advisories)

Evidence

// package-lock.json, line 5 (no "integrity" field)
"node_modules/expresss": {"version": "4.18.2", "resolved": "https://registry.npmjs.org/expresss/-/expresss-4.18.2.tgz"}

npm registry, "expresss" (2026-10-14):
  versions:     ["0.0.0"] only, published 2016-08-15 by a single unrelated maintainer
  description:  "temp test"; no repository, no README
HEAD https://registry.npmjs.org/expresss/-/expresss-4.18.2.tgz -> 404

Risk

  • Wrong package. expresss is not Express, so the app is not getting the framework it presumably expects.
  • Copied version number. The locked version, 4.18.2, matches a real Express release exactly but has never existed under expresss. Copying the real package's version number is a common typosquat trait. The lockfile was hand-edited or produced by something other than the public registry.
  • Open slot. 4.18.2 has never been published under this name, so npm would accept a new upload of it. Whoever controls the expresss name, or takes it over, could publish that version. This project would then install it without any integrity check, including any install scripts. Today, npm ci would simply fail with a 404.

Fix

Replace it with the real package, either "express": "^4.22.3" (latest 4.x) or "^5.3.0". Search the source for require('expresss') or from 'expresss'. Do not just correct the spelling and keep 4.18.2 (see F-06).

F-05

The lockfile and the installed tree disagree, and two of three entries have no integrity hash

Low
Files
package-lock.json lines 4–6; node_modules/
Standards
CWE-353 (Missing Support for Integrity Check); OWASP Top 10:2025 A08 Software or Data Integrity Failures
  • node_modules/ contains only colour-utilz. lodash and expresss are locked but not installed.
  • The installed colour-utilz declares a postinstall script, but its lockfile entry has no "hasInstallScript": true. npm records that flag in lockfileVersion 2 and 3, so the installed package and the lockfile disagree. Either the package changed after the lockfile was written, or the lockfile was edited by hand.
  • expresss and colour-utilz have no integrity field, so nothing ties those entries to specific tarball contents.

Fix

After applying F-01 to F-04, delete node_modules/ and the lockfile. Regenerate them with npm install --ignore-scripts. Review the diff, checking that every entry has integrity and resolves from an expected host, then commit.

  • Its exact-pinned dependencies add 11 more OSV advisories: body-parser@1.20.1 (2), path-to-regexp@0.1.7 (3), qs@6.11.0 (3), send@0.18.0, serve-static@1.15.0 and cookie@0.5.0 (1 each).
  • OSV lists no advisories for express@4.22.3 or express@5.3.0. After reinstalling, run npm audit to check the resolved transitive tree.

Recommended actions

  1. Now: do not run npm install or npm ci on this project until it is fixed. If you have to, add --ignore-scripts.
  2. Remove colour-utilz and find out where it came from (F-01, F-02).
  3. Replace expresss with express ^4.22.3 or ^5.3.0 (F-03, F-06).
  4. Upgrade lodash to ^4.18.1 (F-04).
  5. Regenerate the lockfile cleanly, then run npm audit and npm audit signatures (F-05).
  6. Hardening: commit an .npmrc with ignore-scripts=true and allow install scripts only where needed. Keep internal packages under a scope. In CI, fail the build when lockfile entries lack integrity or resolve from unexpected hosts. Turn on automated dependency alerts (Dependabot or OSV-Scanner).
