Resumen ejecutivo

La base criptográfica es correcta: las contraseñas se derivan con PBKDF2-HMAC-SHA512 (600 000 iteraciones, sal aleatoria por usuario), se comparan en tiempo constante y los tokens de sesión salen de un generador criptográfico. El problema está en el control de acceso a los datos: dos rutas permiten a cualquier usuario autenticado leer información de otros clientes.

  • H-01: el parámetro q de /search se concatena en la sentencia SQL. Un usuario autenticado puede alterar la consulta y leer datos de cualquier tabla, incluidos los hashes de contraseña.
  • H-02: GET /invoices/<id> no comprueba el propietario. Basta con cambiar el identificador numérico para leer cualquier factura, IBAN incluido.

Las dos se corrigen con cambios de una o dos líneas. Les siguen debilidades de sesión, autenticación y despliegue (H-03 a H-07) que conviene resolver antes de cualquier uso real.

Veredicto: no apta para exponerse a usuarios reales hasta corregir H-01 y H-02. H-03 a H-05 deben resolverse antes de pasar a producción.

Detalle de los hallazgos

H-01ALTA

Inyección SQL en /search

app.py, líneas 51-56

Evidencia

if path == "/search":
    q = parse_qs(environ.get("QUERY_STRING", "")).get("q", [""])[0]
    sql = (f"SELECT id, customer, amount FROM invoices "
           f"WHERE owner_id = {user['id']} AND customer LIKE '%{q}%'")
    rows = db().execute(sql).fetchall()

Descripción

q llega de la query string sin validar y se interpola en la sentencia con un f-string. Un valor manipulado puede cerrar el literal y cambiar la estructura de la consulta: anular el filtro owner_id o leer otras tablas. Es la única consulta del proyecto que no está parametrizada; las demás usan ? correctamente.

Impacto

Cualquier usuario autenticado puede leer las facturas de todos los clientes y la tabla users (sal y pw_hash), lo que abre la puerta a ataques de diccionario offline. sqlite3.Cursor.execute() no admite varias sentencias, lo que acota el impacto a lectura y consultas costosas, pero no lo elimina.

Recomendación

Parametrizar la consulta y escapar los comodines de LIKE para que % y _ se traten como texto. Conviene limitar también la longitud de q (por ejemplo, 100 caracteres).

def like_escape(s):
    return s.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_")

rows = db().execute(
    "SELECT id, customer, amount FROM invoices "
    "WHERE owner_id = ? AND customer LIKE ? ESCAPE '\\'",
    (user["id"], f"%{like_escape(q)}%"),
).fetchall()

Referencias

  • MITRE CWE-89: Improper Neutralization of Special Elements used in an SQL Command
  • OWASP Top 10:2021, A03 Injection
  • OWASP ASVS 4.0.3, V5.3.4 (consultas parametrizadas)
  • OWASP Cheat Sheet Series, SQL Injection Prevention Cheat Sheet
H-02ALTA

Acceso a facturas ajenas (IDOR/BOLA) en GET /invoices/<id>

app.py, líneas 39-45

Evidencia

if path.startswith("/invoices/"):
    invoice_id = path.rsplit("/", 1)[-1]
    row = db().execute("SELECT id, owner_id, customer, amount, iban FROM invoices WHERE id = ?",
                       (invoice_id,)).fetchone()
    ...
    return respond(start, "200 OK", dict(row))

Descripción

La consulta filtra solo por id; nunca compara owner_id con el usuario de la sesión. El listado /invoices (línea 48) sí filtra por propietario, así que el control es incoherente entre rutas. Como los identificadores son enteros secuenciales, recorrerlos es trivial.

Impacto

Cualquier usuario autenticado puede leer cualquier factura de cualquier cliente: nombre, importe e IBAN. Es una fuga entre clientes de datos financieros que, si los titulares son personas físicas, también son datos personales.

Recomendación

Filtrar por propietario en la propia consulta y responder 404 (no 403) a las facturas ajenas, para no revelar que existen. Añadir una prueba de regresión: el usuario B recibe 404 al pedir una factura del usuario A.

row = db().execute(
    "SELECT id, customer, amount, iban FROM invoices WHERE id = ? AND owner_id = ?",
    (invoice_id, user["id"]),
).fetchone()
if row is None:
    return respond(start, "404 Not Found", {"error": "not found"})

Referencias

  • MITRE CWE-639: Authorization Bypass Through User-Controlled Key
  • OWASP API Security Top 10:2023, API1 Broken Object Level Authorization
  • OWASP Top 10:2021, A01 Broken Access Control
  • OWASP ASVS 4.0.3, V4.2.1 (protección frente a IDOR)
H-03MEDIA

Tokens de sesión sin caducidad ni revocación

auth.py, líneas 8, 20-22 y 25-29

Evidencia

SESSIONS = {}  # token -> user id (in memory)
...
    token = secrets.token_urlsafe(32)
    SESSIONS[token] = row[0]
...
    uid = SESSIONS.get(header[7:])
    return {"id": uid} if uid is not None else None

Descripción

Los tokens viven en un diccionario de módulo sin marca de tiempo: no caducan por inactividad ni por tiempo absoluto, no existe ruta de logout y no se invalidan al cambiar la contraseña. Además, todas las sesiones se pierden al reiniciar el proceso y no se comparten si se despliegan varios workers.

Impacto

Un token filtrado (registros de un proxy, un dispositivo comprometido, un historial) sigue siendo válido indefinidamente hasta el siguiente reinicio del servicio.

Recomendación

  • Guardar por token el usuario, la fecha de creación y el último uso. Aplicar una caducidad por inactividad (por ejemplo, 30 minutos) y otra absoluta (por ejemplo, 8-12 horas).
  • Añadir POST /logout que elimine el token, e invalidar todas las sesiones del usuario al cambiar la contraseña.
  • Si hay varios procesos, persistir las sesiones en la base de datos guardando solo el SHA-256 del token, no el token en claro.

Referencias

  • MITRE CWE-613: Insufficient Session Expiration
  • OWASP Top 10:2021, A07 Identification and Authentication Failures
  • OWASP ASVS 4.0.3, V3.3.1 (logout y expiración invalidan el token) y V3.3.2 (reautenticación periódica)
H-04MEDIA

Login sin limitación de intentos ni de coste

app.py, líneas 27-33; auth.py, líneas 11-22

Evidencia

def _hash(password, salt):
    return hashlib.pbkdf2_hmac("sha512", password.encode(), salt, 600_000)

def login(username, password):
    ...  # sin contador de intentos, retardo ni bloqueo

Descripción

/login no limita los intentos por cuenta ni por origen. Eso permite adivinar contraseñas en línea, algo especialmente grave porque las cuentas de ejemplo comparten una contraseña conocida (H-10). Además, cada intento contra un usuario existente calcula PBKDF2 con 600 000 iteraciones, un coste de CPU elevado a propósito. Combinado con el servidor monohilo (H-05), un volumen modesto de peticiones sin autenticar puede dejar el servicio sin capacidad para los usuarios legítimos.

Recomendación

  • Limitar los intentos por cuenta y por IP con retardo exponencial o un bloqueo temporal, diseñado para que no se convierta a su vez en un bloqueo de cuentas ajenas. Puede hacerse en la aplicación o en el proxy inverso.
  • Acotar la concurrencia de cálculos de hash (cola o semáforo) para que el login no acapare la CPU.
  • Pedir un desafío adicional (CAPTCHA o segundo factor) tras N fallos.

Referencias

  • MITRE CWE-307: Improper Restriction of Excessive Authentication Attempts
  • MITRE CWE-770: Allocation of Resources Without Limits or Throttling
  • OWASP API Security Top 10:2023, API4 Unrestricted Resource Consumption
  • OWASP ASVS 4.0.3, V2.2.1 (controles anti-automatización)
H-05MEDIA

Servidor de desarrollo wsgiref: sin TLS, monohilo y sin timeouts

app.py, líneas 5 y 61-62

Evidencia

from wsgiref.simple_server import make_server
...
    make_server("127.0.0.1", 8080, app).serve_forever()

Descripción

wsgiref.simple_server se apoya en http.server, que la documentación de Python desaconseja en producción porque solo implementa comprobaciones de seguridad básicas. Sirve HTTP en claro, atiende una petición cada vez y no fija timeouts: un único cliente lento bloquea a todos los demás. El enlace a 127.0.0.1 reduce la exposición, pero en cuanto se publique (directamente o tras un proxy sin TLS) los tokens Bearer y los IBAN viajarán en claro.

Recomendación

Servir la aplicación con un servidor WSGI de producción (gunicorn, uWSGI o waitress) detrás de un proxy inverso con TLS 1.2 o superior, HSTS, timeouts de lectura y escritura y un tamaño máximo de cuerpo.

Referencias

  • MITRE CWE-319: Cleartext Transmission of Sensitive Information
  • MITRE CWE-400: Uncontrolled Resource Consumption
  • OWASP ASVS 4.0.3, V9.1.1 (TLS en todas las conexiones de cliente)
  • Documentación de Python 3, http.server, sección «Security considerations»
H-06BAJA

Lectura del cuerpo de /login sin límite ni validación

app.py, líneas 28-29

Evidencia

size = int(environ.get("CONTENT_LENGTH") or 0)
form = parse_qs(environ["wsgi.input"].read(size).decode())

Descripción

Se lee en memoria tantos bytes como declare el cliente, sin tope. Un Content-Length no numérico provoca ValueError y un cuerpo que no sea UTF-8 provoca UnicodeDecodeError; ambos acaban en un 500 en lugar de un 400. wsgiref devuelve una página 500 genérica, así que no se filtra la traza al cliente: el efecto es de robustez y disponibilidad.

Recomendación

try:
    size = int(environ.get("CONTENT_LENGTH") or 0)
except ValueError:
    return respond(start, "400 Bad Request", {"error": "bad request"})
if not 0 <= size <= 4096:
    return respond(start, "413 Payload Too Large", {"error": "body too large"})
body = environ["wsgi.input"].read(size).decode("utf-8", errors="replace")

Referencias

  • MITRE CWE-20: Improper Input Validation
  • MITRE CWE-770: Allocation of Resources Without Limits or Throttling
  • OWASP API Security Top 10:2023, API4 Unrestricted Resource Consumption
H-07BAJA

Enumeración de usuarios por tiempo de respuesta

auth.py, líneas 17-19

Evidencia

row = con.execute("SELECT id, salt, pw_hash FROM users WHERE username = ?", (username,)).fetchone()
if row is None or not hmac.compare_digest(_hash(password, row[1]), row[2]):
    return None

Descripción

Si el usuario no existe, la evaluación en cortocircuito evita calcular el hash y la respuesta es inmediata. Si existe, se calculan 600 000 iteraciones de PBKDF2. Aunque el mensaje de error es el mismo en los dos casos (bien hecho), la diferencia de tiempo, del orden de cientos de milisegundos, revela qué nombres de usuario son válidos.

Recomendación

Calcular siempre el hash, contra una sal y un hash ficticios cuando el usuario no exista:

_DUMMY_SALT = secrets.token_bytes(16)
_DUMMY_HASH = _hash(secrets.token_urlsafe(16), _DUMMY_SALT)

salt, stored = (row[1], row[2]) if row else (_DUMMY_SALT, _DUMMY_HASH)
ok = hmac.compare_digest(_hash(password, salt), stored)
if row is None or not ok:
    return None

Referencias

  • MITRE CWE-208: Observable Timing Discrepancy
  • OWASP WSTG v4.2, WSTG-IDNT-04 Testing for Account Enumeration and Guessable User Account
H-08BAJA

Exposición excesiva de datos en el detalle de factura

app.py, líneas 41 y 45

Descripción

El detalle devuelve dict(row) completo, con el IBAN entero y el owner_id interno. Aunque se corrija H-02, el cliente no necesita el identificador interno del propietario y probablemente tampoco el IBAN completo.

Recomendación

Devolver una lista explícita de campos, quitar owner_id y enmascarar el IBAN (por ejemplo, solo los cuatro últimos caracteres) salvo en las operaciones que de verdad lo necesiten.

Referencias

  • MITRE CWE-200: Exposure of Sensitive Information to an Unauthorized Actor
  • OWASP API Security Top 10:2023, API3 Broken Object Property Level Authorization
H-09BAJA

IBAN y hashes en SQLite sin cifrar y con permisos por defecto

app.py, línea 9; auth.py, línea 7; seed.py, líneas 6 y 10

Descripción

invoices.db guarda IBAN en claro y los hashes de contraseña. SQLite crea el fichero con permisos 0644 (sujetos a la umask), es decir, legible por otros usuarios locales. La ruta es relativa ("invoices.db"), así que el fichero acaba en el directorio desde el que se lance el proceso y puede terminar en un directorio servido o en una copia de seguridad sin control.

Recomendación

Usar una ruta absoluta configurable fuera de cualquier directorio publicado y permisos 0600. Valorar el cifrado del IBAN a nivel de campo o un volumen cifrado, y aplicar a las copias de seguridad la misma protección.

Referencias

  • MITRE CWE-312: Cleartext Storage of Sensitive Information
  • OWASP ASVS 4.0.3, V6.1.3 (datos financieros regulados cifrados en reposo)
H-10BAJA

Contraseña fija y compartida en el script de carga

seed.py, líneas 8 y 15

Evidencia

DROP TABLE IF EXISTS users; DROP TABLE IF EXISTS invoices;
...
(uid, name, salt, hashlib.pbkdf2_hmac("sha512", b"demo-password", salt, 600_000))

Descripción

Todos los usuarios de ejemplo reciben la misma contraseña, escrita en el código. Es aceptable en una demo, pero si este script se usa para crear un entorno compartido, cualquiera que lea el repositorio puede entrar en todas las cuentas. Además, el script borra las tablas sin preguntar: lanzado por error contra una base real, destruye los datos.

Recomendación

Generar una contraseña aleatoria por usuario (secrets.token_urlsafe) y mostrarla una sola vez, o leerla de una variable de entorno o de getpass. Impedir que el script se ejecute fuera de desarrollo, por ejemplo exigiendo un indicador explícito.

Referencias

  • MITRE CWE-259: Use of Hard-coded Password (CWE-798, Use of Hard-coded Credentials)
  • OWASP ASVS 4.0.3, V2.10.4 (secretos fuera del código fuente)
  • OWASP Top 10:2021, A07 Identification and Authentication Failures

H-12INFO

Cabeceras de seguridad ausentes y métodos HTTP sin restringir

app.py, líneas 18-20 y 39-56

Descripción

respond() solo envía Content-Type. Las respuestas con datos financieros no llevan Cache-Control: no-store ni X-Content-Type-Options: nosniff. Las rutas de lectura (/invoices, /invoices/<id>, /search) aceptan cualquier método HTTP.

Recomendación

Añadir esas dos cabeceras en respond() y devolver 405 Method Not Allowed a los métodos no previstos.

Referencias

  • MITRE CWE-525: Use of Web Browser Cache Containing Sensitive Information
  • OWASP ASVS 4.0.3, V8.2.1 (cabeceras anti-caché), V14.4.4 (nosniff) y V14.5.1 (solo los métodos HTTP en uso)
H-13INFO

Conexiones SQLite que nunca se cierran

app.py, líneas 12-15, 41, 48 y 55; auth.py, línea 16

Descripción

Cada petición abre una conexión nueva que nunca se cierra explícitamente y depende del recolector de basura. Con carga sostenida puede agotar descriptores de fichero. Ojo: usar la conexión como gestor de contexto (with sqlite3.connect(...)) solo confirma o revierte la transacción, no la cierra.

Recomendación

from contextlib import closing

with closing(db()) as con:
    rows = con.execute(...).fetchall()

Referencias

  • MITRE CWE-772: Missing Release of Resource after Effective Lifetime

Aspectos positivos

  • Contraseñas derivadas con PBKDF2-HMAC-SHA512, 600 000 iteraciones y sal aleatoria de 16 bytes por usuario (auth.py:12, seed.py:13-15), por encima de las 210 000 que recomienda el OWASP Password Storage Cheat Sheet para esa variante.
  • Comparación del hash en tiempo constante con hmac.compare_digest (auth.py:18).
  • Tokens de sesión de 256 bits generados con secrets.token_urlsafe(32) (auth.py:20).
  • Consultas parametrizadas en el login, el detalle, el listado y el script de carga. Solo /search se sale de la norma.
  • El mismo mensaje de error tanto si el usuario no existe como si la contraseña es incorrecta (app.py:32).
  • Token en la cabecera Authorization y no en cookies: no hay superficie CSRF.
  • Respuestas JSON con Content-Type: application/json; no se refleja HTML.
  • El servidor se enlaza a 127.0.0.1 por defecto.
  • Solo usa la biblioteca estándar: no hay dependencias de terceros que vigilar.

Plan de remediación

1. Inmediato

H-02 (filtrar por owner_id) y H-01 (parametrizar /search), con pruebas de regresión que comprueben el aislamiento entre usuarios. Son cambios pequeños y cierran las dos vías de acceso a datos ajenos.

2. Antes de producción

H-03 (caducidad y logout), H-04 (limitación de intentos), H-05 (servidor de producción con TLS), H-06 (límite del cuerpo) y H-07 (hash constante).

3. Endurecimiento

H-08 a H-13: minimizar la respuesta, proteger la base de datos en reposo, sustituir la contraseña fija del script de carga, añadir registros, cabeceras y cierre de conexiones.

Metodología y supuestos

  • Método: revisión manual línea a línea de los cuatro ficheros del alcance, siguiendo el flujo de cada ruta desde la entrada (PATH_INFO, query string, cuerpo y cabecera Authorization) hasta la base de datos y la respuesta.
  • Sin pruebas dinámicas: la aplicación no se ejecutó. Los hallazgos se confirmaron leyendo el código; como es breve y los fallos no dependen de configuración, la confianza es alta.
  • Dependencias: no hay manifiesto (requirements.txt o similar) y el código solo importa la biblioteca estándar, así que no se hizo análisis de composición de software. La versión de Python no consta; se supone Python 3 con soporte vigente.
  • Supuesto de despliegue: la severidad se valoró pensando en un uso multiusuario real, que es lo que sugiere el modelo de datos con owner_id. Como demo local en 127.0.0.1, el riesgo práctico es menor.
  • Escala de severidad: Alta: cualquier usuario autenticado accede a datos de otros sin condiciones especiales. Media: debilita controles de autenticación, sesión o disponibilidad, o requiere condiciones adicionales. Baja: impacto acotado o que requiere acceso local o privilegiado. Informativa: defensa en profundidad.
